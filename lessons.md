# Lessons Learned

## 2026-06-19 (later) — Sidestep before you solve: changing the data avoided the unification work

- **The cheapest fix to a type-inference gap can be to remove the call that triggers it.** `base.asl`'s `Bitset.init` was calling `bits = Array.init(size)` — a function call returning `Array[Any]` with the Any generic left free, which then failed to match `Bitset.bits: Array[u8]` downstream. The "proper" fix was the equality-vs-unification rewrite of the analyzer's type-match path (already a TODO). The actual fix that landed was changing one line of `base.asl` to `bits = Array[u32] { size: size }` — the struct initializer requires explicit impls (already enforced), so the result is `Array[u32]` directly, no inference involved. The integration suite went from 15/35 to 17/35 without any analyzer code changes. The lesson isn't "always pick the cheap fix" — the unification gap is still real and will bite later — but "the design discussion you're about to start may not be necessary if you can express the same intent with the syntax that already works." In this case, the phantom-as-field brainstorm (a meaningful refactor) wasn't required to make this fixture compile.
- **Removing dead surface area before fixing what's left.** Same commit dropped ~195 lines from `base.asl` — the speculative `read` / `write` / `valid` / `Pointer` / `System` layer that no fixture actually exercised. Less surface means fewer places for the next analyzer change to ripple to. Worth doing before each large pass on the analyzer, not after.
- **`loc: Location` threaded explicitly beats `valType.loc`.** The `analyzeValueTypeAgainstDefinitionType` overloads were reporting type-mismatch errors at `valType.loc` — which for a generic-typed value points at *the generic's declaration*, not at the kwarg/arg site where the mismatch happens. Threading an explicit `loc: Location` parameter through the overload chain and using it in every error path makes diagnostics actually point at user-fixable code. Every recursive call passes the same loc — the location stays "the original use site," not whatever sub-position the recursion descends into.

## 2026-06-19 — Field-vs-source distinction in AnalyzedGetter; explicit-impl escape hatch hits real code

- **`getter.argType` should be the field's type, not the source's.** First pass at `AnalyzedGetter` stored `argType: AnalyzedArgumentType` set to the source variable's type (so for `pair.first` where `pair: Pair[u8, u8]`, `getter.argType` returned `Pair`). The consumer that mattered was `argType*(AnalyzedExpression)` for `aekGetter` — meaning "what's the type of this expression?" — which under that shape gave the source object's type instead of the field's, so a let-binding `let x = pair.first` would type `x` as `Pair`, not `u8`. Renaming the stored field to `source` and routing the `argType*` accessor through `property.argType` corrects the expression semantics without touching the constructor's parameter order. The lesson: when a single field name has to carry the meaning of two distinct things ("what's the source" vs "what's the expression's value type"), naming the field after one and accessing the other through the property model is cleaner than overloading the field's role.
- **The explicit-impl escape hatch shows up the moment a real fixture needs it.** Day-one usages in `examples/base.asl` already use the new `Status[u64].Err {…}` / `Status[Array[Any]].Err {…}` / `Status[Bitset].Err {…}` syntax — the cases where the Err variant only binds `Error`, leaving `Any` (Status's other position) genuinely undeterminable by leave-as-is. We argued during design that the escape hatch would be the rare case; in practice it's surfacing every time the user writes an `Err` arm in a match. That's a useful signal that the urkImpl form isn't just a theoretical fallback — it's load-bearing.
- **Per-receiver-kind dispatch on the public filter.** `analyzeFunctionCall` was calling `findFunctionDefs(name, arity, public)` with `public = module != definedType.module.resolved` — fine for module receivers (only external calls need public), but generics don't have a public-or-private declaration on their funcDefs at all. The fix dispatches on `definedType.kind`: modules apply the external-vs-internal rule; generics always pass `true` (any funcDef is callable). Worth flagging: an accessor-asserted field (`definedType.module.resolved`) was being read unconditionally before the case, which would have crashed on generic receivers as soon as one came through — the dispatch fix also closes that latent kind-assert.

## 2026-06-18 — Union-initializer inference: mirror what works

- **Mirror the shape that already works, including the `Ref` indirection.** Struct initializers already carried `StructRef` (tagged union over default {module} and impl {argType}), with parser/resolver/analyzer all dispatching on its kind. Bringing union initializers up to the same expressiveness was almost entirely a mechanical mirror: `UnionRef` / `ResolvedUnionRef` / `AnalyzedUnionRef`, `urkDefault` / `urkImpl`, `analyzeUnionRef` next to `analyzeStructRef`, etc. Naming each layer's kind enum after its predecessor (`srk` → `rsrk` → `asrk`; `urk` → `rurk` → `aurk`) made the symmetry visible in source. The only real divergence was the analyzer body: struct's impl arm doesn't substitute (phantom-types stay opaque to data), but the union's impl arm does, because the variant's field types reference the union's generics directly.
- **Leave-as-is is cheap when the param list is positional.** With `genericTypeIndex: Table[GenericArgumentType, int]` already on the union, the default-arm flow is one walk of the kwargs (accumulating a `GenericImplMap` via merge) plus one walk of the param table (filling impls — bound positions get the concrete from the map, uncovered positions get the generic itself wrapped as a free AnalyzedArgumentType). No special "is this generic free" data; the impl is either a concrete module type or a generic argument type, and downstream `concrete()` already knows what to do with either. The whole leave-as-is implementation is twenty lines.
- **Treat integration-test failure-mode shifts as progress.** After this change `nimble test` stays at 197/197 and `./test.sh` stays at 15/35 — both look static. But the *reason* twenty fixtures fail changed: from `base.asl:229:15 failed to find matching function` (literal-arg inference, marker held for weeks) to `:0:0 case block return types are not same` (the case-arm uniformity check using `==` where it should use unification). The pipeline now runs past the union initializer for those fixtures and surfaces the next pre-existing TODO. When the headline numbers don't move but the failure modes do, that's signal — it tells you which TODO is now the bottleneck. Watch the failure messages, not just the count.
- **Asymmetric semantic difference: struct impl arm vs union impl arm.** Designing the urkImpl analyzer arm was a moment of "wait, struct doesn't do that." The struct's phantom-type impls (`Array[Any] {…}`) live in the requires block, not in the field types — so substituting into the data fields would do nothing. The union's impls feed directly into variant field types via `value: K`, `error: K`, etc. — so the impl arm has to actually substitute, while the struct's stays a no-op pass-through. Same outer shape (`Ref` indirection, dispatch on kind), different inner work. A reminder that "mirror it" doesn't always mean "identical implementation" — sometimes the shape mirrors but the semantics demand more.

## 2026-06-17 — Generic concretization landing: position-indexed param lists

- **Store the position index, derive the list from it.** Earlier the union's deduped requires list was computed by walking variants and pushing into a `HashSet[Generic]` + parallel `seq`. The analyzer's `concrete()` then had to take an `implMap: Table[ResolvedGeneric, AnalyzedArgumentType]` keyed by generic identity. Two representations of the same information, kept in sync by hand. The new shape stores a single `Table[ResolvedGenericArgumentType, int]` on `ResolvedStruct` and `ResolvedUnion`, where `int` is the position in the requires list. The `requires*` accessor materializes the seq from the index (`newSeq[ResolvedGenericArgumentType](idx.len)` + fill by index). Downstream substitution is `impls[idx[generic]]` — one lookup, no map merging. The same index mirrors to `AnalyzedStruct` / `AnalyzedUnion` so concretization at the analyzer level uses positional rewrite, not name-keyed map traversal.
- **Mutate-and-thread is the right shape for accumulator passes that span variants.** `resolveVariant` (and `analyzeVariant`) take a `var Table[ResolvedGenericArgumentType, int]` parameter — the union's shared index, mutated as each variant's fields are walked. The `accumulateGenericPosition` helper takes a field at a time and assigns the next position if the generic is new; repeats keep the position they already have. Same mechanism handles within-struct, within-variant, and cross-variant occurrences uniformly — no special-casing.
- **Don't duplicate semantic checks that exist downstream.** First pass shipped a `validateUniqueGenericFields` that rejected duplicate generic names at the resolver — `first: K, second: K` in a struct, K shared across variants of a union, etc. The intent was to push errors to definition time. But the analyzer's `GenericImplMap.merge()` already binds one generic to one concrete type per construction, so any *actual* conflict ("K binds to u8 here and String here") surfaces with a clear error at the init site. The resolver-stage rejection was preemptive validation of something the analyzer already enforced — relocating the error from analyzer-stage to resolver-stage, not adding any guarantee. Dropped the check, upgraded the merge error message with a "declare a second generic if you need independent types" hint, and the language gained flexibility (Rust-style enum sharing) without losing any safety. The lesson: when a downstream phase already enforces a rule semantically, an upstream check is *only* an error-message-quality lever, not a correctness mechanism. Decide whether it's worth the code on UX grounds alone.
- **Equality and unification are different operations once values can carry free generics.** Today `AnalyzedArgumentType.==` is hash-equality. Once leave-as-is inference lands (a value of type `Box[u8, Sample]` with `Sample` still parametric), assignability against an expected `Box[u8, MyImpl]` needs unification, not equality. Distinct concerns: type identity (deduplication, table keying — equality) vs assignability (arg-vs-arg-def matching, return-vs-expected — unification). Marked the eventual audit with a TODO on every callsite; the trap is real and would only surface once free generics are actually produced.
- **Build the design via a multi-turn back-and-forth before any code.** The whole union-generics design — variants of the rule, syntax for explicit impls, the leave-as-is interpretation, error UX — went through eight turns of conversational design before the first commit. Each turn ended with a focused question that narrowed the design space by one decision. Tried option A, surfaced its edge case, user proposed B, ran edge cases on B, etc. The shipped rule (no resolver-stage uniqueness + analyzer-stage merge as the actual enforcer + leave-as-is for partial-coverage variants + explicit-impl escape hatch) is internally consistent and was *cheap* to converge on because nothing was implemented prematurely. The arc here is also a lesson: the first implementation enforced uniqueness at the resolver, lived for two commits, and got peeled back once the redundancy with `merge()` became visible. Cheap to add, cheaper to remove than to live with.

## 2026-04-16 — ExternFunction and the Function union

- **Functions are a tagged union, not a single type.** The original `Function` type assumed every function has a body (`StatementList`). Extern functions (`@extern("symbol")`) have no body — they're a symbol name + function definition. Rather than adding an `Option[StatementList]` field (which would require nil-checks everywhere), split into `UserFunction` (decorators + def + body) and `ExternFunction` (symbol + def), wrapped in a `Function` tagged union (`fkUser | fkExtern`). Callers that need name/def/arity dispatch on kind; callers that need the body only accept `UserFunction`.
- **Extern function indentation is the same level as user functions, not nested.** First attempt had `@extern(...)` at module-body indentation and the `func` line indented one level deeper (like a block body). But the actual syntax has both at the same level — `@extern("u8_read")` on one line, `public func read(...)` on the next, both at 2-space module-body indentation. The parser's `level` should not be incremented between the two lines.
- **Try the more specific spec first in `oneOf`-style fallbacks.** `funcBlockSpec` tries `externFunctionSpec` before `userFunctionSpec`. An extern function starts with `@extern(` which immediately disambiguates — if `@` fails, fall back to user function. This avoids the user function spec consuming `@extern` as a decorator and then failing on the missing body.
- **Standard library as an ASL file.** `examples/base.asl` defines the full standard library (u8-u64, i8-i64, f32, f64, pointer, String, Error, Status, System, Array, Bitset) using extern functions. This makes the base types first-class ASL modules rather than compiler magic — the compiler just needs to know the extern symbol names. New grammar features (`literal:`, `requires()`, `public generic`) are used in base.asl but not yet parseable; the extern function parsing works for all modules that don't use those features.

## 2026-04-13 — Absorbing the validator and deleting the resolver

- **Push validation into constructors, not into a separate phase.** The validator existed as a separate compiler phase (`parse → index → resolve`) with its own `Indexed*` wrapper types. Every uniqueness check it performed (duplicate fields, duplicate variants, duplicate module/generic names, module-must-have-data-or-function, import-name collisions) could be expressed as a precondition in the AST constructor that receives the relevant list. `newStruct(fields)` can check for duplicate field names because it sees the full field list. `newFile(path, imports, items)` can check for import-vs-module collisions because it sees both lists. Moving checks into constructors means invalid AST nodes can never be constructed — the invariant is "if the node exists, it's valid." A separate validation phase means "the node exists but might be invalid until you run validation." The constructor approach is strictly stronger.
- **Index tables belong on the AST types, not on wrapper types.** The validator's `IndexedStruct` wrapped a `Struct` and added a `fieldIndex: Table[string, int]`. But the parser's `Struct` already had the fields — why not put the index there? Once the constructor builds the index during construction (for duplicate detection), the index is available for free to all downstream phases. The wrapper layer (`Indexed*`) was pure indirection.
- **If your wrapper type adds only indices and no validation, it's dead weight.** After moving all checks into constructors, the validator's `index*` procs did nothing but iterate children and populate Tables — the exact same work the constructors now do. The entire `src/validator/` directory (3 files, ~230 lines) was deleted with no loss of functionality.
- **Unreachable defensive checks should be assertions, not error paths.** The validator's "duplicate file paths" check in `index(files)` could never fire because the parser's BFS uses a `HashSet` that guarantees unique paths. Keeping it as a `Result` error path adds dead code and makes the function signature heavier (`Result[App, string]` vs plain `App`). Either delete it or make it an `assert` — don't pretend it's a user-facing error.
- **Delete the resolver if nothing consumes its output.** The resolver built `Resolved*` wrapper types with local IDs and resolved type references — but `asl.nim` did `let _ = ? resolve(app)`, discarding the result. The only real value was two validation checks (unknown type, import name not found) that could live elsewhere. Deleting the entire resolver (-664 lines) simplified the pipeline to just `parse` and unblocked a clean rewrite.
- **Constructor guards as defense in depth.** `newStruct` now rejects `fields.len == 0` even though the grammar's `atLeastOne(fieldLineSpec)` should prevent it. This guard exists because a blank line after `struct:` bypasses `atLeastOne` via a grammar-level backtracking bug. The guard doesn't currently fire, but it prevents a malformed struct from ever being constructed if the grammar bug is triggered. Pattern: always validate constructor preconditions even when the grammar "should" guarantee them.
- **The pipeline should be as short as possible.** Started at `parse → index → resolve`. After absorbing the validator: `parse → resolve`. After deleting the resolver: just `parse`. Each elimination removed a phase boundary, eliminated wrapper types, and simplified `asl.nim`. Add phases back only when they produce output a downstream consumer actually reads.

## 2026-04-12 — Component directory modules (project structure)

- **`nim.cfg` with per-component `path` entries is the mechanism, not `foo/foo.nim`.** Nim's directory module convention (`import foo` finding `foo/foo.nim`) didn't fully work — types from the directory module weren't resolving correctly with just `--path:src`. Adding each component directory explicitly (`path = "$projectDir/tokenizer"`, etc.) to `src/nim.cfg` is what makes bare `import tokenizer` work from inside `src/parser/grammar.nim`. The `.nimble` file's `switch("path", "src")` wasn't picked up by the compiler at all — `nim.cfg` in the source directory is the reliable mechanism.
- **`$projectDir` in nim.cfg resolves to the directory containing the main `.nim` file.** Since `src/asl.nim` is the entry point and `srcDir = "src"`, `$projectDir` points to `src/`. This makes `path = "$projectDir/parser"` resolve to `src/parser/`, which is exactly what we want.
- **Split atomic, not incremental, when moving to component directories.** The parser split (1868 lines → 5 files) had to be a single commit because intermediate states (e.g., combinators extracted but grammar still in the old file) wouldn't compile — grammar.nim needs types from combinators.nim and ast.nim simultaneously. Trying to split one piece at a time leads to broken intermediate builds. Accept the large commit and verify with `test.sh` afterward.
- **Export internal types just enough for sibling files in the same component.** `ParserError` and `Parser` were private (no `*`) when everything was in one file. After splitting into `combinators.nim` and `grammar.nim`, `grammar.nim` needs access to both types. Solution: add `*` to the type declarations in `combinators.nim`. They don't leak to external consumers because `parser/parser.nim` (the entry point) only re-exports `ast` and `loader` — not `combinators`.
- **Private field mutation across module boundaries needs a setter.** `loader.nim` does `imp.path = depPath` but `path` is a private field on `Import` defined in `ast.nim`. Within one file this works; across modules it doesn't. Fix: add `proc 'path='*(imp: Import, p: string)` in `ast.nim`. General pattern: any field mutated from outside its defining module needs an explicit setter proc.
- **Re-export entry points keep consumer imports unchanged.** `parser/parser.nim` is just `import ast, loader; export ast, loader`. Consumers (`validator.nim`, `resolver.nim`, `asl.nim`) still write `import parser` and get everything they need. The directory structure is invisible to consumers. Same pattern for `validator/validator.nim` and `resolver/resolver.nim`.
- **`type File = parser.File` disambiguation proliferates.** After the split, any new file that imports `tables` (which transitively imports `syncio`) and also imports the parser's `File` type needs the disambiguation. It appeared in `grammar.nim`, `loader.nim`, `indexed.nim`, `indexer.nim`, `types.nim`, `resolve.nim`. Accept the boilerplate — it's one line per file and prevents a confusing "ambiguous identifier" error.
- **Validate the path mechanism with the smallest component first.** Phase 1 moved only `tokenizer.nim` (132 lines, zero internal imports) to `src/tokenizer/tokenizer.nim`. This surfaced the `nim.cfg` discovery (that `.nimble` `switch("path", ...)` doesn't work, that directory module convention alone is insufficient) without risking a broken parser. Only after the tokenizer move succeeded with 35/35 tests did we proceed to the complex parser split.
- **Each component directory gets one line in nim.cfg.** The pattern is mechanical: `path = "$projectDir/<component>"`. Adding a new component (e.g., `analyzer/`) requires one line. No other configuration changes.

## 2026-04-02 01:12 — Bug audit and CLI hardening

- Bare `except:` in Nim catches everything including `Defect` — always use `except CatchableError:` at minimum, and narrow further when exception types are known.
- `changeFileExt("")` on a file without an extension returns the same filename — enforce `.asl` extension on source files to prevent output overwriting input.
- Use plain `object` for small, short-lived data (CLI config, tokens). Use `ref object` for recursive, large, or widely-shared data (AST nodes, IR, symbols, types). Excessive `object` copying caused real perf issues during prototyping.
- `ref object of RootObj` is only needed when inheritance or runtime type checks (`of`) are required — don't use it by default.
- Pin nimble dependencies to exact versions (`==`) for a mission-critical compiler. Open ranges (`>=`) risk silent breakage from upstream updates.
- `switch("experimental", "dotOperators")` is intentional — used for short-circuiting in the compiler.
- `.gitignore` for Nim projects should include `nimcache/`, `nimbledeps/`, `*.o`, `*.so`, `*.dylib` beyond just the binary.
- File existence validation is a parsing concern, not an argparse concern — but deferred for now since the compiler is under active development.
- `parseInt(...).uint8` for `indentWidth` is safe when constrained by argparse `choices` — no need to over-engineer it.

## 2026-04-02 02:41 — CLI refactor with variant objects and help command

- argparse raises `ShortCircuit` (a `CatchableError`) on `--help` — must be caught explicitly before the general `CatchableError` handler, otherwise help requests look like errors.
- Nim variant objects (`case kind: EnumType`) are the idiomatic way to model command sum types — each variant carries only its relevant fields, enforced at compile time.
- Separate types per command (`AslBuildCommand`, `AslHelpCommand`) keeps concerns isolated and makes the CLI extensible for future commands.
- Return `Result`-based accessors on variant fields (e.g., `proc build*(cmd): Result[AslBuildCommand, string]`) to prevent unsafe variant access at runtime.
- `--help` should print to stdout with exit code 0. Errors should print to stderr with exit code 1. These are distinct paths — don't conflate them through the same `err()` return.
- Bare `asl` with no subcommand returns `err(Usage)` — prints to stderr, exits 1. Some CLIs treat this as implicit `--help` (stdout, exit 0). Design choice to revisit later.
- Always rebuild after code changes before testing — stale binaries cause confusion (e.g., old `ShortCircuit` error persisting after the fix).

## 2026-04-02 03:44 — Source encoding validation and Trojan Source defense

- Nim's `runes` iterator and `fastRuneAt` assume valid UTF-8 — they produce garbage or crash on invalid bytes. Always validate UTF-8 first before iterating runes.
- Trojan Source attacks use bidi codepoints (U+202A–U+202E, U+2066–U+2069), zero-width characters (U+200B–U+200D, U+FEFF), and invisible control characters to make source code appear different from what the compiler sees. A mission-critical compiler must reject these.
- Write bite-sized composable functions: `isBidiCodepoint`, `isZeroWidthCodepoint`, `isInvisibleCodepoint` → `classifyDangerous` → `scanDangerousCodepoints` → `validateSourceEncoding`. Each does one thing, `?` chains them.
- Pass `uint32` to codepoint checker functions instead of `Rune` — the checks are purely numeric, no need to carry the `Rune` type through.
- `validateUtf8` from `std/unicode` returns byte offset of the first invalid byte, or -1 if valid. Use a separate `byteOffsetToLineCol` helper to convert to human-readable positions.
- TOCTOU: `fileExists` followed by `readFile` is a race condition. Better to let `getFileSize`/`readFile` fail and catch `IOError` in one `try/except` block.
- `Result[void, T]` is a good pattern for validation functions — `ok()` means passed, `err(T)` carries the classification or error message.

## 2026-04-02 04:44 — Code consistency pass and cleanup

- Error messages from inner functions should be lowercase with no prefix. The `[ERROR] -` prefix belongs at the display boundary (`asl.nim` main) — not in library code. This keeps errors composable.
- If a one-line wrapper function adds no logic, inline it. `validateSourceEncoding` was just `? scanDangerousCodepoints(...)` — removed in favor of calling directly.
- Use `case` over `if/elif` on variant objects — Nim's exhaustive matching catches unhandled variants at compile time. Critical as the command set grows.
- All `case` statements should use trailing colon (`case x:`) for consistency.
- Export `$` on all public types — if one type's `$` is exported, all sibling types should match.
- Invalid UTF-8 errors should report byte position, not line:col — editors can't render the broken bytes meaningfully anyway, so byte offset is more actionable.
- BOM (`U+FEFF`) is rejected everywhere — intentional strict policy for ASL source files.
- When a bug is already fixed by prior changes, verify before attempting a fix — avoids redundant edits.

## 2026-04-02 07:12 — Tokenizer design and debug infrastructure

- The tokenizer is intentionally dumb — it's a per-rune character classifier. Multi-character tokens, keywords, strings, numbers, indentation, and comment handling are all parser concerns.
- Name functions for what they actually check. `validateUtf8` was renamed to `isCompilerSafe` — it checks for dangerous codepoints, not UTF-8 encoding validity.
- Nim `set` can't hold `uint32` values properly (warning for >65535). Use typed `array` with `contains`-based `in` lookup instead.
- `r.uint32 <= 0x7F` is the correct way to check if a rune is ASCII — it's a semantic check. `r.size == 1` gives the same result but answers a different question.
- `r.char` only works safely for ASCII runes. For non-ASCII it truncates to the low byte.
- All valid ASCII is valid UTF-8 — ASCII (0x00–0x7F) is a subset of UTF-8.
- Debug dump flags (`--dump-tokens`, future `--dump-ast`, etc.) should be per-stage. Dump to stdout so it can be piped. Gate behind the flag — never dump unconditionally. Pipeline continues after dumping.
- Empty files are valid — the tokenizer returns an empty `seq[Token]` and the parser handles structural validation.
- Trailing newlines are normalized by the tokenizer — inject a newline token at the end if missing, so the parser always sees a consistent stream.
- Span tracking (start + end position) is unnecessary when the tokenizer is single-character. Can be added later if the tokenizer becomes multi-character.
- Null bytes get rejected as unknown tokens by the existing `else` branch — no special handling needed.

## 2026-04-05 10:55 — Parser audit and design observations

- The parser is a recursive descent backtracking parser built on top of a dumb single-character tokenizer. It combines raw tokens into multi-character constructs (identifiers, strings, numbers, etc.) — this complexity lives in the parser by design, not the tokenizer.
- Checkpoint/restore pattern for backtracking: `parse` procs save `parser.index`, try a spec, and restore on failure. Clean and predictable.
- `ParserError` with `Location` and `<` operator lets `max(errors)` pick the deepest error — the one that got furthest before failing. Good heuristic for error reporting in backtracking parsers.
- Inline vs block parser specs (`InlineParserSpec` vs `BlockParserSpec`) separate parsers that don't care about indentation from those that do (via `level: uint32`).
- Watch for variant object field access bugs — accessing `node.strLit` when you meant `node.strContent` compiles if both variants have the same field types but is a runtime bug. Nim's variant objects don't protect against this at compile time when using `ref object`.
- Self-referential `value` procs are a common copy-paste bug — `assignment.value` calling itself instead of `assignment.target` causes infinite recursion.
- When two parse alternatives start with the same token pattern (e.g., expression and assignment both start with an identifier), ordering matters for performance. Put the one with the earlier disambiguator first (assignment has `=` after the identifier).
- `ref object of RootObj` should not appear unless inheritance is needed — it was found on `StatementList` with nothing inheriting from it.

## 2026-04-06 — Parser combinator architecture design

- The `AslNode` variant object is the main obstacle to adding new syntax — every new node type requires ~6 touch points (enum, variant field, constructor, loc dispatch, value dispatch, assert at call site). It exists solely as a uniform return type for parse functions.
- The real AST types (`Expression`, `Statement`, `Module`, etc.) are already independent `ref object`s. `AslNode` is a redundant wrapper — eliminate it by making parse functions return concrete types.
- Parser combinators absorb the repetitive patterns: `oneOf` replaces the try-collect-errors-return-max pattern (~5 instances), `any`/`atLeastOne` replace the while-isOk loops (~8 instances), `separatedBy` replaces the A-comma-A loops (~3 instances).
- `Spec[T] = ref object` with generic `T` is the right combinator type for Nim. Being a `ref object` enables forward declaration for recursive grammars — create the spec with `parseFn: nil`, fill in the implementation later. Closures in other specs that capture this ref see the updated `parseFn` at parse time.
- Every `Spec` carries a `name: string` for two reasons: (1) error messages — `oneOf` can say "expected {spec.name}" when all alternatives fail, (2) identity — forward-declared specs are identifiable before they have an implementation.
- Sequencing should NOT be a combinator — just use normal Nim code with `?` operator. The `run` method on each sub-parse provides backtracking. The caller's `run` restores the index if the whole sequence fails. This hybrid (declarative combinators + imperative sequencing) is the pragmatic sweet spot for Nim.
- Core combinator set: `oneOf[T](name, specs) -> Spec[T]`, `any[T](spec) -> Spec[seq[T]]`, `atLeastOne[T](spec) -> Spec[seq[T]]`, `optional[T](spec) -> Spec[Option[T]]`, `separatedBy[T,S](spec, sep) -> Spec[seq[T]]`, `map[T,U](spec, name, fn) -> Spec[U]`.
- `run[T](parser, spec) -> Result[T, ParserError]` replaces both `InlineParserSpec` and `BlockParserSpec` — generic over return type, with automatic checkpoint/restore.
- `map` combinator bridges between parse results and AST nodes. E.g., `stringLiteralSpec.map("string_expr", proc(s): Expression = newExpression(s))` converts a `Spec[StringLiteral]` to `Spec[Expression]` for use in `oneOf`.
- Block-level (indentation-aware) specs need `level: uint32` — handled by closures that capture the level, not by a separate spec type.
- `contained[T](name, open, inner: Spec[T], close) -> Spec[T]` is a higher-level combinator for delimited containers. It handles: open delimiter, optional whitespace, inner spec, optional whitespace, close delimiter. Composes with `separatedBy` — container handles delimiters, `separatedBy` handles comma-separated content. Captures three recurring patterns in the parser: `(..args)`, `[..types]`, `{..fields}`.

## 2026-04-06 — Parser combinator refactor execution

- `separatorSpec(sep)` factory generalizes the "optional_spaces separator optional_spaces" pattern. Used for `,`, `:`, `=` — adding a new separator is one line.
- `escapedSpec(char, charSpec)` factory unifies punctuation and alphabet escape handling. Adding a new escape sequence is one line + adding to the `oneOf` array.
- `unescapedStringCharSpec` must reject both `"` and `\` — not just `"`. The old code only rejected `"`, which would have caused `\` to be consumed as a regular character instead of starting an escape sequence.
- Nim's `result` is a special variable inside procs (implicit return value). Naming a local variable `result` inside combinator closures triggers `ResultShadowed` warnings. Use `res` or `maybeValue` instead.
- Nim's `options` module (`Option[T]`, `isSome`, `get`) must be explicitly imported in `parser.nim` — the linter removed the re-export from `combinator.nim`.
- Forward-declared specs (`newSpec[T]`) work because `Spec[T]` is `ref object` — closures capture the ref, not the parseFn. When the parseFn is set later, all closures see the update at parse time. Two forward-declared specs in the parser: `argumentTypeSpec` (self-referential generics) and `expressionSpec` (mutual recursion with argumentList via functionCall).
- `expressionSpec.parseFn = oneOf(...).parseFn` — assign the parseFn from a combinator result to a forward-declared spec. The `oneOf` creates a new spec; we extract its parseFn and assign it to the existing ref.
- When `any(combinator)` backtracks a failed iteration, it also undoes any "ignorable line" consumption from within that iteration. This can leave trailing newlines unconsumed. The `fileSpec` loop needs `if parser.done(): break` after consuming ignorable lines to handle trailing whitespace at end of file.
- `statementListSpec` is `atLeastOne(statementLineSpec)` where each statementLine is `indentation + statement + newline`. The combinator replaces a 15-line manual while loop with a one-liner.
- `functionListSpec` is `any(functionBlockSpec)` where each block skips leading ignorable lines then parses a function. `any` backtracks the ignorable line consumption if no function follows.
- Block-level specs (statementList, function, functionList, module) are simple `let` declarations, not factory procs. `parser.level` is a field on Parser — `blockSpec` increments it for body parsing, `run` saves/restores it on backtracking alongside `parser.index`.
- `blockSpec[H, B, R](name, header, body, combine)` is the higher-level combinator for indented blocks: `indentation + header + newline + body(level+1)`. Used by `functionSpec`, `moduleSpec`, `genericSpec`. Adding a new block type is: define header spec, pick a body spec, one `blockSpec` call.
- Don't over-generalize header specs — `moduleHeaderSpec` and `genericHeaderSpec` look the same today (`keyword name :`) but may diverge (e.g., function definition is already a different header shape). Keep them separate.
- `parser.filepath` belongs on Parser — it's needed by `fileSpec` to construct `File` directly. Without it, you'd need intermediate tuple types (`FileContent`) to pass data between `fileSpec` and the `parse*` entry point.
- `File` stores `imports`, `modules`, `generics` as separate arrays. `newFile` accepts `seq[Type]` and filters by kind — the sum type (`Type`) is only used during parsing, the `File` type keeps the concerns separated.
- Import syntax: `import { Name, Name } from "path"`. Uses `contained` for the braced name list and `separatedBy` for comma-separated identifiers. `keywordSpec("from")` matches the source keyword.
- File grammar is `import* (module | generic)*` — imports must come before modules/generics. `fileSpec` parses `any(importBlockSpec)` first, then `any(typeBlockSpec)`.
- `value` procs on AST types became dead code after the combinator refactor — the `compile` function in `asl.nim` discards the parsed `File` and returns the raw source. Removing them also eliminated the `strutils`/`sequtils` imports.
- Linters may add `?` to `discard parser.run(...)` calls, turning optional parses into required ones. This silently breaks parsing when the consumed element isn't always present (e.g., optional spaces before `(`). Review linter changes carefully on Result-returning expressions.

## 2026-04-07 — Expression types, error propagation, and linting

- Expression ordering in `oneOf` follows specificity: string literal (starts with `"`), float literal (digit with `.` or `e`), integer literal (digit), initializer (identifier + `{` or space+literal), function call (identifier + `.` + name + `(`), getter (identifier + `.`), variable (bare identifier — always last, catches anything).
- `Literal` is a variant (string | integer | float) shared between expressions and primitive initializers. Expression has a single `ekLiteral` variant that forwards to `Literal`, avoiding three separate literal variants.
- Integer literal is itself a variant: `UnsignedIntegerLiteral` (`digit+`) and `SignedIntegerLiteral` (`(+|-) unsigned`). The sign is required for signed — a bare `42` is unsigned, `-42` is signed.
- Float literal requires either decimal part or exponent to distinguish from integer: `3.14` and `1e10` are floats, `42` is not. Tried before integer in `oneOf` since integers are a prefix of floats.
- Initializer is a variant: primitive (`identifier space+ literal`, e.g., `u8 0`) and non-primitive (`argumentType { kwargs }`, e.g., `Array[u32] { size: 10 }`). Primitive uses plain identifier for type, non-primitive uses `argumentType` (supports generics).
- Fatal error propagation: when `blockSpec`'s header succeeds but body fails, the error is marked `fatal: true`. `run` skips backtracking for fatal errors, `any` propagates them instead of silently returning partial results. This ensures error messages point to the real failure, not a misleading indentation mismatch at a higher level.
- `asl` methods on AST types use bottom-up approach: inline types return `string`, block types return `seq[string]`. Parents indent child lines by `" ".repeat(indentWidth)`. No `depth` tracking — indentation compounds naturally.
- Reuse existing types: `ArgumentDefinition` (`name: Type`) serves as struct fields, union variant fields, and function arguments. No need for separate `FieldDefinition` type.

## 2026-04-08 — Data blocks in modules

- Module body is `optional(dataBlock) + functionList`. Data block is `oneOf(struct, union)`. Must appear before functions if present.
- Struct block: `struct:` + field lines where each field is an `ArgumentDefinition`. No name on the struct — it's implicitly the module's data layout.
- Union block: `union:` + variant lines. Each `VariantDefinition` has a name and optional fields in braces (`Free { usage: u32 }`). Fields reuse `ArgumentDefinition` inside `contained("{", separatedBy(...), "}")`.
- Nameless block headers (`struct:`, `union:`) return just `Location` from their header spec. `blockSpec` handles them the same as named headers — the combine function ignores the location if not needed.
- Module body became a composite spec (`ModuleBody` tuple) since `blockSpec` takes a single body spec. The tuple `(Option[DataBlock], FunctionList)` is unpacked in the combine function.

## 2026-04-11 — Resolver layout pass + example coverage audit

- **Group types, constructors, accessors, and the derivation proc for each concept.** First draft of `resolver.nim` had all types in one block at the top, all accessors next, all `resolveX` procs at the bottom. Reviewing a single concept (e.g. `ResolvedFunction`) meant scrolling to three different places. Moved each type into its own `type` block followed immediately by its `newResolvedX` constructor, `id*`/`name*`/... accessors, and the `resolveX(rawAstNode)` proc. Reviewing one concept now means reading ~40 contiguous lines. Forward references work within a single-file Nim module as long as the dependency graph is a DAG (it is — no mutual recursion among resolved types).
- **Compute children first, construct parent once.** Original `resolveFunction` built the wrapper with empty `params`, then mutated it via `for p in ... rf.params.add(...)`. Switched to computing the `var params: seq[ResolvedArgument]` locally first, then constructing the final `ResolvedFunction(...)` in one shot at the end. No mutation after construction, all fields visible in one place at the call site, easier to audit for completeness. Applied uniformly to every resolve proc that has a loop.
- **Uniform `newResolvedX` constructors over ad-hoc object literals.** Mirrors the `newX` pattern in `parser.nim`. Benefits: (1) single place to change if field semantics evolve, (2) the call site reads like a domain operation (`newResolvedFunction(id, decorators, name, params, ...)`) rather than a struct literal, (3) future refactors (like renaming fields) need only touch the constructor, not every resolve proc. For variant types (`ResolvedData`), two overloaded constructors mirror `parser.newDataBlock`.
- **Store derived data at the source, not at the consumer.** First draft: `resolveImport` called `resolveImportPath(imp.source, importingFile)` to recompute the absolute path. But the parser's BFS already computes this during dependency traversal — it just threw the result away after enqueueing. Moved the `path: string` field onto `parser.Import` and populated it inside the BFS loop. The resolver now reads `imp.path` directly; `resolveImportPath` goes back to being a private parser helper. Lesson: if you catch yourself recomputing something a previous phase already knew, the phase boundary is in the wrong place.
- **Test fixtures surface bugs that type systems miss.** Writing `examples/errors/missing_file.asl` crashed the compiler with an unhandled `OSError` — `readFileSafe` had caught only `IOError` but on macOS `getFileSize` throws `OSError` for missing files. The bug had been dormant since the file reader was written; no existing test touched it because every fixture referenced files that existed. Lesson: negative test fixtures aren't just there to verify error messages — they're there to force the compiler to walk code paths no positive test hits. Every new negative fixture has a nontrivial chance of discovering a latent crash.
- **`fileExists` upfront + `CatchableError` for everything else.** The fix wasn't "add `OSError` to the except list" — that would leave the next OS-level exception just as unhandled. Instead, handle the common case (missing file) explicitly with `fileExists` before any filesystem call, then catch `CatchableError` (not just `IOError`) for any remaining unexpected failure. Covers permission errors, symlink loops, filesystem corruption, etc. without playing whack-a-mole with exception types.
- **Annotate every fixture with what it tests.** The parser accepts `#` line comments, so each file in `examples/` and `examples/errors/` can carry a leading doc-comment explaining which feature or validation rule it exercises. Before: 24 files with no indication of intent, reviewers had to read the body to guess. After: skim the first 3–4 lines of any fixture and you know why it's in the suite. Bonus: moved line numbers for the negative fixtures (the errors now point deeper into the file because of the prepended comment block) verified that location tracking worked through comment-line skipping.
- **Audit existing coverage by listing the full language surface.** After adding the comments, went through every major feature (struct/union, match, imports, generics, function overloading, signatures, decorators, type refs, ...) and asked "do we have a positive and negative fixture for this?". Several gaps: zero-arg function, nested generic type params, pure-generic file, duplicate variant field, parent-directory import escape, missing file, cyclic imports, duplicate names within a single import brace group. Each gap became a single small fixture. The coverage audit surfaced two latent issues (the `OSError` crash above, and the implicit-allow policy for multiple imports from one path) that formal test planning would have caught earlier.
- **Probe grammar decisions with disposable `/tmp` files before committing fixtures.** For each candidate new fixture, wrote a minimal version in `/tmp/probe_*.asl` and ran `./asl build` to see what happened. Confirmed some assumptions were wrong (empty `struct:` is currently *allowed* by the grammar — probably a latent bug, noted for later) and avoided committing fixtures that would have been miscategorized.

## 2026-04-11 — ID-based structural resolution (PSR-41 Phase 1)

- **Build the Resolved tree as a separate module.** The same wrapper-types pattern used for `validator.nim` (PSR-39) paid off again for `resolver.nim`. Parser AST stays untouched; validator's `Indexed*` stays untouched; a new `Resolved*` tree mirrors the App hierarchy and replaces every name with a local `id: int` + raw `Identifier`. Each phase lives in its own file; the pipeline is `parse → index → resolve`. Adding a phase doesn't touch earlier phases — the extra indirection is worth it.
- **Speculative type-level infrastructure is a trap.** First draft had 12 typed global-id objects (`FileId`, `ModuleId`, `FunctionId`, `FieldId`, `ArgumentId`, each a little variant union encoding the ancestor path). Four successive simplification passes stripped them out: the argument/field types unified, then data-vs-computation split them again, then the whole typed-id scheme was dropped in favor of plain `int`. Phase 1's real requirement was "every declaration stores its position in its parent". A plain int does that. Everything else was infrastructure for a hypothetical consumer that doesn't exist yet — defer until Phase 2 or 3 actually wants it.
- **Bite-sized commits, one block type per commit.** 15 commits, roughly 20–50 LoC per diff, each compiled clean and kept every existing example green. Ordering mattered: introduce the leaf type first (`ResolvedField`, `ResolvedArgument`) in a standalone commit, then the container (`ResolvedStruct`, `ResolvedFunction`) that uses it, then wire it into the parent (`ResolvedModule`). The sequence lets each commit be reviewed in isolation.
- **Separate "data member" from "computation input" at the type level.** `ArgumentDefinition` is one parser type used for struct fields, variant fields, function params, and funcDef params. In the resolved tree, struct/variant fields become `ResolvedField` and params become `ResolvedArgument`. Structurally identical, different type names. The type system now catches passing a struct field where a function parameter is expected — useful once Phase 3 starts resolving expression references to field accesses vs. variable lookups.
- **Keep the Identifier around alongside the id.** Each resolved declaration still carries its original `Identifier`. The `id` gives the position; the `Identifier` gives the textual name and its `Location` for error messages and diagnostics. Cost: one ref per node. Value: the resolver errors can still point at exact `line:col` even when their only direct output is an integer id.
- **Two-pass resolution for cross-block references.** `ResolvedImport.targetFileId` needs to look up the imported file in `ResolvedApp.fileIndex`. But `fileIndex` is populated *during* file resolution. Solution: first pass builds `fileIndex` by iterating `app.files` and recording every path, then the second pass actually builds `ResolvedFile` entries. Simpler than a topological DAG solve for a single forward reference.
- **Export types lazily as call sites demand.** Each commit only exported from `parser.nim` the types it actually needed (`Decorator`, `ArgumentType`, `StatementList`, etc.) and added the accessors (`Module.decorators`, `Module.loc`, `FunctionDefinition.params`, etc.) on the fly. Avoids a big "export everything" commit that changes the surface without a clear reason. Each export has a commit that justifies it.
- **Plan revision cycles are cheap compared to wrong commits.** The plan file (`plans/id-resolution.md`) got rewritten four times before any code landed — each round shrinking the design (typed ids → per-context typed ids → unified argument id → field-vs-argument split → no typed ids at all). Every revision was <100 LoC of markdown; every would-be-wrong commit avoided was 30–50 LoC of code + the cost of reverting it. Doing the design iteration in the plan document kept the git history clean.
- **Don't split commits by what's "interesting" — split by what's independently reviewable.** Even the final "dull" commits (R2 ResolvedFile with just id + path, R6 ResolvedGeneric skeleton) earned their own commit because each one is a single focused change against a green tree. Every commit stands alone in review.

## 2026-04-11 — Threading source locations via `Identifier` (PSR-40)

- **Raw strings discard the location.** The original AST stored every name (`Module.name`, `Struct` field names, `VariantDefinition.name`, etc.) as `string`. `identifierSpec` already returned an `Identifier { value, loc }`, but every constructor extracted `.value` and threw `.loc` away. The validator could only report `file.asl: duplicate name 'Foo'` — no line, no column. Lesson: when the parser already carries provenance, don't drop it in the AST. Keep the richer type all the way to the error emission site.
- **The refactor is mechanical once you commit to it.** Swap `name: string` for `name: Identifier` on every declaration-site field, flip each constructor signature, fix the one-line call site in the spec where `.value` was being extracted, and update `asl()` formatters. ~20 AST types, ~24 parser call sites, ~15 formatters. No algorithmic rework needed.
- **Bite-sized sequencing is the right pace for this refactor.** Splitting into 14 commits (one field or tight pair per commit) kept each diff ~20–50 lines, each commit individually reviewable, each intermediate state green. Phase B (5 commits on validator-visible names) shipped a user-visible line:col improvement per commit, which made the progress concrete. Phases C and D had no visible payoff but unblock name resolution and type checking. Large "refactor the whole codebase" patches would have been unreviewable.
- **Indexed lookup tables still key on `string`, not `Identifier`.** `Table[string, int]` continues to map textual names to positions. The AST carries `Identifier`; the validator just extracts `.value` at the insertion site. Two separate concerns: lookup identity (textual) vs. source provenance (location-carrying). Conflating them would force reference-equality keying and break lookups.
- **Two `.name` fields at different layers is confusing.** After the first pass, the common chain was `module.name.name` — one `.name` is the accessor on the AST type, the other is the internal textual field on `Identifier`. Renaming `Identifier.name` → `Identifier.value` fixes the ambiguity: outer `.name` consistently means "the identifier on this AST node"; inner `.value` consistently means "the textual name". The chain now reads `module.name.value` / `module.name.loc`. Worth doing when a naming collision causes visible awkwardness.
- **`Option[Identifier]` beats `""`-as-sentinel.** `ImportedType.alias` was originally `string` with empty-string meaning "no alias". Converting to `Option[Identifier]` kills the sentinel, makes the absence explicit, and (because `Option[Identifier]` carries a full identifier) gives the validator a loc to point at when the collision is on the aliased name rather than the original. General pattern: any time you see an empty-string-as-absent check, consider whether `Option[T]` would model it better.
- **Redundant `loc` fields disappear once names carry their own.** `Decorator` used to have both `name: string` and `loc: Location`. The loc was always the location of the name identifier. After `name` becomes `Identifier`, the separate `loc` field is dead weight — delete it in the same commit, don't leave it for later.
- **Declaration order matters when the old leaf starts depending on the new one.** `Decorator` sat above `Identifier` in the file because nothing in `Decorator` needed `Identifier`. Once `Decorator.name: Identifier`, the compiler errored (`undeclared identifier: 'Identifier'`). Fix: move the `Identifier` type block above any type that now references it. Easy to miss because Nim doesn't auto-hoist type refs.
- **`tables` transitively imports `syncio`, so `File` collides.** When `validator.nim` imported `tables`, `parser.File` and `syncio.File` became ambiguous. Local `type File = parser.File` alias fixes it cleanly without sprinkling `parser.File` throughout the module.
- **Watch for forgotten `aslBlock` formatters.** The match-assignment path has its own `aslBlock(stmt, indentWidth)` branch that formats `stmt.assignment.target` directly — it's not reached by the standard `asl(Assignment)` formatter. The build error surfaced only after the final regression compile. Lesson: when refactoring a field that's formatted in multiple places, `grep` for the field name, not just the primary accessor.

## 2026-04-10 — Block indexing and validation

- Reframe "validation" as "indexing". Six validation rules (unique names, non-empty file, non-empty module, etc.) look like separate checks, but uniqueness is a free side effect of constructing `Table[string, int]` lookup tables. The type-resolution phase needs `findModule`/`findFunction`/`findField` anyway, so building the indices upfront gives you the checks *and* the lookups in one pass. Only the non-uniqueness rules (#2 "file has ≥1 module or generic", #4 "module has data or ≥1 function") remain as explicit checks.
- Wrapper types over AST mutation. Instead of adding private index fields to every AST node in `parser.nim`, `validator.nim` defines `Indexed*` wrappers (`IndexedFile`, `IndexedModule`, `IndexedStruct`, …) that hold a reference to the raw AST plus their indices. Keeps parser.nim free of indexing concerns, localizes all find procs next to the indexing logic, and avoids mutating parsed AST after the fact.
- `Result[App, string]` over `Result[void, string]`. Early draft had `proc index(block): Result[void, string]` that mutated index fields in place. The wrapper redesign naturally flipped this to `proc indexModule(m: Module): Result[IndexedModule, string]` — build the indexed wrapper from scratch and return it. Eliminates partial-state concerns and makes the control flow trivially correct.
- Single namespace across modules/generics/imports. The rule "no duplicate names in a file" must check three indices in parallel: adding a module checks against all modules *and* all generics *and* all imports already indexed. Same for generics and imports. This models the actual language semantics (an imported `X` shadows/collides with a locally-defined `X`) rather than enforcing three separate uniqueness rules.
- Overloading is the one exception. Only functions allow same-name duplicates, so their index is `Table[string, seq[int]]`. Everything else (modules, generics, fields, variants, struct/variant fields) is `Table[string, int]` and fails on duplicate insertion. Lookups return `@[]` or `-1` on miss — callers check before indexing.
- Readonly accessor procs over public fields. Pattern used throughout: `proc name*(m: Module): string = m.name`. The field stays private in `parser.nim`, consumer modules get readonly access via the accessor. Makes the AST effectively immutable from outside parser.nim without needing any distinct type or copy.
- Assert on variant access in conditional accessors. When a `case kind:` object has per-variant fields (`DataBlock.struct`, `DataBlock.union`), the accessor procs must assert the variant before returning (`assert db.kind == dbkStruct, …`). Without the assert, Nim's RTTI would `FieldDefect` with a less helpful message — and forgetting the assert risks garbage reads on mis-typed callers during refactors.
- `parser.File` vs `syncio.File`. The moment `validator.nim` imports `tables` (which transitively imports `syncio`), `File` becomes ambiguous. Two fixes: qualified use (`parser.File`) everywhere, or a local alias (`type File = parser.File`) at the top of the module. The alias is cleaner when the module uses `File` heavily.
- Negative test fixtures require fully valid surrounding syntax. First attempt at `dup_module.asl` had `func a(x: i64): i64` with no body, so the parser errored on indentation (a function *inside a module* requires a body) before ever reaching the indexing phase. Lesson: when testing error messages from later phases, every *other* part of the input must parse clean.
- `changeFileExt`-style stray binaries. `nim c src/validator.nim` (used to sanity-check the new file in isolation) emits a binary at `src/validator` with no extension. `nimble build` produces only `./asl`. Stray binaries creep into `src/` and need cleanup. Prefer `nim check src/validator.nim` for type-checking without codegen.

## 2026-04-08 — Match expressions and decorator scoping

- Match is a block expression (`ekMatch`) not a block statement — it can be assigned (`y = match x:`) or standalone. Parsed separately in `statementLineSpec` since it handles its own indentation via `blockSpec`. `expressionSpec` intentionally excludes match to prevent it from appearing in inline contexts (function call arguments, etc.).
- Match expression as subject of another match is explicitly rejected in `matchBodySpec` with a guard check (`subject.kind == ekMatch`). Currently also implicitly prevented because `expressionSpec` doesn't include match, but the explicit check protects against future changes.
- `statementLineSpec` tries match patterns (standalone and assigned) before inline statements. Match handles its own indentation via `blockSpec`, so it's tried before `indentationSpec` is consumed for inline statements.
- `statementListSpec` is forward-declared (`newSpec`) for mutual recursion: match → caseBlock → statementList → statementLine → match.
- Block statements need multi-line formatting. `aslBlock(stmt, indentWidth)` returns `seq[string]` — dispatches to `asl(matchExpr, indentWidth)` for match, wraps in `@[asl(stmt)]` for inline. Match assignment formatting: first line is `target = match subject:`, rest are case block lines.
- Not all blocks support decorators. `blockSpec` (plain) is for case, struct, union, generic. `decoratedBlockSpec` adds decorator parsing for module and function only. This prevents accidental `@export` on blocks that don't support it.
- Types involved in mutual recursion must share one `type` block: `Expression`, `Assignment`, `CasePattern`, `CaseBlock`, `MatchExpression`, `Statement`, `StatementList` all reference each other and must be defined together.
